## 1. 产品判断

### 1.1 这个产品到底是什么

它**不是一个好看的落地页**，而是一件**会自己证明自己的工程作品**：

> 一个想走后端与 AI 方向的大一学生，用一个月写出来的个人主页 ——
> 它的**架构、API、测试、部署流水线、AI 问答本身，就是这个学生的简历**。

访客看的不只是「你做了什么」，而是「**你做事的方式**」：有没有文档、有没有测试、有没有把密钥藏好、API 挂了会怎样。这些细节比排版更能说明问题。

### 1.2 用户与「30 秒任务」

| 用户 | 他想要什么 | 对应设计 |
| :--- | :--- | :--- |
| 面试官 / HR | 30 秒判断「这人靠不靠谱」 | 首屏一句话定位 + 3 个项目卡 + 简历 + 邮箱一键盘复制 |
| 技术学长 / 同行 | 看代码、看你怎么想 | 仓库链接、API 文档、架构文档、笔记 |
| 同学 / 未来的自己 | 记录与检索 | 笔记系统、标签、搜索、近况时间线 |
| 自己 | 学会后端与 AI | 站点本身就是练手场（API + 数据库 + RAG） |

**首屏 30 秒必须传达**：① 我是谁（大一，主攻后端与 AI）→ ② 我做过什么（3 个可点开的项目）→ ③ 怎么联系我。

### 1.3 成功标准（v1.0 发布时须同时成立）

**产品侧**
- 手机打开 3 秒内看到名字与定位，无横向滚动、无字体过小。
- 首屏可见 ≥ 3 个**真实**项目（不是「建设中」占位），其中 ≥ 1 个可在线访问、≥ 1 个是可运行的 API。
- 访客能在 2 次点击内拿到联系方式（复制邮箱 / GitHub / 简历）。
- 站点包含 ≥ 5 篇真实笔记。

**工程侧**
- 内容与代码分离：新增项目/笔记不需要改 HTML。
- 后端具备：版本化 API（/api/v1）、OpenAPI 文档、健康检查、限流、统一错误格式。
- 前台在 API 不可用时**自动降级**，页面仍然完整可读。
- 仓库无任何明文密钥；CI 全绿；有一次可回滚的版本 tag。
- Lighthouse（移动端）：性能 ≥ 90、无障碍 ≥ 95、最佳实践 ≥ 95、SEO ≥ 95。

**个人侧**
- 每周至少 1 篇笔记；每两周至少 1 次对外可见的发布。
- 你能**独立讲清楚**每一版的架构决策（讲不清 = 没学会，需要复盘）。机制见 §9 与 `docs/LEARNING.md`（D47：每版末 5 问，答案由本人写）。

### 1.4 最大风险：不是代码，是内容

一个只有炫酷首页、项目全是「施工中 🚧」的作品集，说服力为 **0**；一个排版朴素但有 3 个能跑的真实项目的站点，说服力很高。

因此本路线图设有**双轨**（§3）：工程轨负责「货架」，作品轨负责「货」。**两轨必须同时推进，任何一轨停摆，v1.0 都不算成功。**

## 2. 约束与边界

### 2.1 硬约束

| 约束 | 说明 | 对规划的影响 |
| :--- | :--- | :--- |
| 时间 11 周（2026-10-12 → 12-27） | 且 **2027 年 1 月初是期末考试周** | v1.0 必须赶在 12 月底前发，留 1 月缓冲；不能压到 1 月 |
| 人力 | 1 人（大一在读），预估 8–10 小时/周 | 总量约 90–110 小时，决定 §6 砍单顺序 |
| 能力 | 后端与 AI 入门，前端薄弱 | 前端全部交给 Claude Code + 可运行方案；学习时间留给后端/AI |
| 托管 | GitHub Pages 免费、纯静态 | 前端必须静态；后端必须另找免费托管 |
| 预算 | 目标 0 元 | LLM 与数据库都必须用免费额度，并设熔断 |

### 2.2 明确不做（Non-goals）

> 这些不是「以后再说」，而是**在 v1.0 之前一律不碰**。写下来是为了在动摇时有据可依。

1. **不引入 React / Vue / Next.js / Svelte。** 收益低、挤占后端时间；原生 JS + 构建工具足够。
2. **不做用户系统**（注册/登录/JWT/权限）。v1.0 不需要，且是安全风险重灾区。
3. **不做 SSR / 自建服务器 / 自建数据库服务器。** 静态托管 + 免费 PaaS 足够。
4. **不做复杂 CMS 后台。** 内容用 Markdown 文件 + Git 就是最好的 CMS。
5. **不做小程序 / 移动 App。**
6. **不追测试覆盖率数字。** 只覆盖关键路径（API 契约、AI 输入校验、内容渲染）。
7. **不做多皮肤 / 多主题 / 国际化**（除非 §6 触发）。
8. **不刷框架名词。** 技能区只写真正用过的东西。
9. **不为了上线而伪造内容。** 没做的项目写「计划中」，但不能标「已完成」。

### 2.3 时间预算（必须先接受这个现实）

| 项目 | 估算 |
| :--- | :--- |
| 每周可用 | 8–10 h（工作日 × 1.5h + 周末 2h） |
| 11 周总量 | 约 90–110 h |
| v0.2 工程基线 | 12 h |
| v0.3 笔记系统 | 14 h |
| v0.4 门面达标 | 8 h |
| v0.5 后端 API | 18 h |
| ~~v0.6 数据库+留言板~~ **已砍**（2026-10-11，平台无持久磁盘） | 0 h（原估 10 h 释放给 v0.6 收口 / v0.7 的 4 周） |
| v0.7 AI 问答 | 16 h |

## 3. 两条轨道

### 轨道 A —— 工程轨（站点本身）

| 版本 | 产出 | 你学到 |
| :--- | :--- | :--- |
| v0.2 | 构建流水线 + 内容层 | 工程化、CI/CD、静态资源部署 |
| v0.3 | 笔记子系统 | 数据建模、路由、Markdown 渲染 |
| v0.4 | 体验与无障碍 | 前端工程质量、性能与可访问性 |
| v0.5 | 后端 API v1 | HTTP、REST、FastAPI、OpenAPI、CORS、部署 |
| v0.6（重定义） | 站点自身收口 | 404 页、隐私说明页、无障碍与真机复测、Lighthouse 复测（原「数据库与写路径」**已砍**，持久化延后 v1.1） |
| v0.7 | AI 问答（RAG） | 嵌入、向量检索、Prompt、流式输出、成本控制 |
| v0.8 | 稳定化 | 测试、日志、监控、安全 |
| v0.9 / v1.0 | 发布 | 版本管理、发布流程、文档 |

### 轨道 B —— 作品轨（货架上的货）

> **关键设计：轨道 B 的产物就是轨道 A 的功能，一次劳动两份收获。**

| 编号 | 时间 | 作品 | 产出物 | 对应站点 |
| :--- | :--- | :--- | :--- | :--- |
| **B1** | 已完成（原 W1–W3） | 数据小工具 CLI | Python + Pandas：读 CSV → 清洗 → 统计 → 出图；README + 成果图 | 项目卡 1（repo: `Mucheng-zzb/data-toolkit`） |
| **B2** | 已完成（原 W4–W7，实际 2026-10-11） | 第一个 REST API | FastAPI：**只读** API（7 个 GET 端点）+ 统一错误体 + X-Request-Id + 契约测试 + /docs + Docker 部署；**SQLite 与 CRUD 延到 v1.1**（v0.6 已砍，D51） | **直接成为站点 v0.5 的 API** |
| **B3** | v0.7：11/09–12/06 | AI 问答（RAG） | 索引 + 嵌入 + 向量检索 + Prompt + 流式/非流式 | **直接成为站点 v0.7 的 AI 功能** |
| **B4** | 可选 | 一个小模型实验 | scikit-learn 分类或 PyTorch 小 demo + 一篇笔记 | 项目卡 4 或笔记 |

**这条设计的妙处**：B2、B3 不是「额外的作业」，而是站点必须做的功能。你不必在「做作品集」和「学后端」之间二选一。

**飞轮**：写笔记 → 笔记成为 AI 问答的语料 → AI 问答变聪明 → 站点更有说服力 → 更想写笔记。
所以 **v0.3 的笔记不是装饰，是 v0.7 的燃料**。越早开始写，后面越省力。

## 5. 逐版本规划

### v0.2 —— 工程基线 + 内容数据化（W1–W2，10/12–10/25）

**目标**：把「手写单页」升级为「有构建、有内容层、有自动部署、有质量基线」的工程。

**为什么现在做**：后面每一版（笔记、API 联调、测试、CI、AI 功能）都建立在这套地基上。晚做一次，就要迁移两次。

**范围（做）**
1. 引入 **Vite**（vanilla 模板 + 原生 JS，**不装任何 UI 框架**），提供 dev / build / preview 三个脚本。
2. 目录重构为 monorepo：`web/`（前端）、`api/`（先放占位 README）、`docs/`、`.github/workflows/`。
   - **过渡状态（v0.2-A 实测）**：根目录的 `index.html` / `script.js` / `style.css` 作为**临时保活副本**保留 —— 因为此时 GitHub Pages 仍从分支根目录部署。**真值来源是 `web/`**，根目录三件套不再接受功能改动，待 v0.2-B 切到 Actions 部署后删除。
3. **内容层**（把硬编码内容抽成数据）：
   - `web/content/profile.json`（姓名、定位、社交链接、邮箱）
   - `web/content/projects/*.md`（front-matter 元数据 + 正文）
   - `web/content/now.json`（近况时间线）
4. **渲染层**：`web/src/` 按职责拆分（`main.js` / `ui/*` / `lib/*`），项目卡、技能标签、时间线全部由数据渲染。
5. **降级**：首屏关键内容（姓名、定位、邮箱、GitHub）保留在 HTML 里，禁用 JS 时仍然可见 —— 保住 v0.1 的这条底线。
6. **CI/CD**：GitHub Actions 构建并把 `web/dist` 发布到 Pages（`actions/configure-pages` + `actions/upload-pages-artifact` + `actions/deploy-pages`）。保留旧的「从分支部署」作为回滚路径。
7. **质量基线**：Prettier + ESLint（flat config）+ `npm run check`；Lighthouse CI 只**记录**分数到 `docs/BASELINE.md`，先不设门禁。
8. 重写 README：面向开发者（环境、脚本、目录、部署、如何加内容）。

**明确不做**：不换视觉风格、不改配色、不加新板块、不写后端代码、不使用任何前端框架。

**验收标准（逐条可验证）**
- [ ] `npm ci && npm run build` 在干净目录成功，`web/dist` 为纯静态文件。
- [ ] 推到 `main` 后 3 分钟内线上更新，URL 不变：https://mucheng-zzb.github.io/personal-portfolio/
- [ ] **新增一个项目 = 在 `web/content/projects/` 加 1 个 .md 文件并提交**，页面自动出现，全程不改 HTML。
- [ ] 禁用 JavaScript 后，姓名、定位、邮箱、GitHub 依然可见。
- [ ] `npm run check` 无错误；Lighthouse 基线分数已记录。
- [ ] **（v0.2-A）** 根目录三副本相对 v0.1 **仅有注释差异**（实测 `git diff` = **11 增 0 删**）——即搬家过程中没有夹带任何功能改动。
- [ ] **（v0.2-B 硬门禁）** 删除根目录 `index.html` / `script.js` / `style.css` 后，**线上仍正常**；用 `git ls-files` 确认根目录不再有这三件套。

**`npm run check` 现状（v0.2-A 实测）**
v0.2-A 的 `npm run check` 只是 `vite build` 的**占位**，**不是代码检查** —— 它不会发现任何格式或 lint 问题，不要把它当质量门禁读。
真实质量基线（Prettier + 可选 ESLint + Lighthouse 记录）在 **v0.2-D** 落地并**替换** `check`。
纪律：将来引入 Prettier **必须是独立 commit**，**不得与功能性改动混提**，否则格式化噪音会淹没真实 diff。

**风险与对策**
- ⚠️ **Pages 子路径**：项目页部署在 `/personal-portfolio/` 下，Vite 的 `base` 必须设为 `'/personal-portfolio/'`，否则 CSS/JS 404。
- ⚠️ **Actions 权限**：仓库 Settings → Pages → Source 要改成 **GitHub Actions**；workflow 需要 `pages: write` 与 `id-token: write`。
- ⚠️ **file:// 直接打开会失效**（ES module 与 fetch 受 CORS 限制）。这是**有意接受的取舍**：从此开发用 `npm run dev`，README 里写清楚。

**可砍**：ESLint（保留 Prettier）；Lighthouse CI（保留手动跑一次记录基线）。

### v0.3 —— 笔记子系统（W3–W4，10/26–11/08）

**目标**：让站点从「一次性展示页」变成「会持续生长的内容站」，同时**为 v0.7 的 AI 问答积累语料**。

**为什么现在做**：① 它是作品轨 B1/B2 的天然载体；② 它是 AI 功能的燃料；③ 它把「更新网站」的成本降到写一个 Markdown 文件。

**范围（做）**
1. `web/content/notes/*.md`，front-matter：`title / date / tags / summary / draft`。
2. 列表页 + 详情页。**路由决策：使用 hash 路由**（`#/notes`、`#/notes/<slug>`）—— 因为 GitHub Pages 不支持服务端重写，history 路由刷新会 404。
3. Markdown 渲染：`marked`（或 markdown-it）+ `DOMPurify` 清洗；代码高亮用 `highlight.js` 或 `shiki`（二选一，别都装）。
4. 标签筛选、上一篇/下一篇、预计阅读时长。
5. 首页展示最近 3 篇笔记。
6. `draft: true` 的文章不进入构建产物。
7. `robots.txt` + `sitemap.xml`（构建时生成）。

**明确不做**：不做全文搜索（先用标题+标签+摘要过滤）；不做文章评论；不引入 SSG 框架（Astro/Next）。

**验收标准**
- [ ] 新增一篇笔记只需新增 1 个 .md 文件。
- [ ] 笔记链接可直接复制分享，刷新不 404。
- [ ] `draft: true` 的文章在构建产物中不存在（用 grep 搜标题验证）。
- [ ] 列表页在 20 篇笔记下滚动流畅，首屏无布局跳动。

**风险与对策**

### v0.5 —— 后端 API v1（W6–W7，11/16–11/29）★ 里程碑

> **实际：2026-10-11 完成并打 tag v0.5.0**（比计划提前约 5 周）；提前的时间用于 v0.5.x 加固与内容轨，**不提前上 v0.6**。

**目标**：上线**第一个属于你自己的公网后端服务**，并让前端真正消费它。

**为什么现在做**：这是整条路线里**含金量最高的一版**。它把「我在学后端」从一句话变成一个有 URL、有文档、有健康检查的真实服务。

**范围（做）**
1. `api/`：**FastAPI**（Python，与你的后端/AI 方向一致）。分层：`routers/`（路由）、`services/`（业务）、`models/`（schema）、`core/`（配置、日志、错误）。配置走环境变量，`.env.example` 入库、`.env` 入 `.gitignore`。
2. **只读 API**（数据源先用仓库里的 Markdown/JSON 解析，不依赖数据库）：
   - `GET /api/v1/health`、`/profile`、`/projects`、`/projects/{slug}`、`/notes`、`/notes/{slug}`、`/now`（共 7 个）
   - 统一错误格式、`X-Request-Id` 中间件、结构化日志。
   - 自动生成 **OpenAPI 文档**（`/docs`）。
3. **CORS 白名单**：只允许 GitHub Pages 域名 + localhost。
4. **部署**到免费 PaaS（选型与「部署前现查」清单见 `docs/ARCHITECTURE.md` ADR-005），配置健康检查与自动部署。
5. **前端接入**：`web/src/lib/api.js` 统一请求封装（超时、重试、错误处理）。
6. **降级**：API 不可用时，项目/笔记回退到**构建期内置的数据**，页面完整可用，只在页脚提示一句「显示的是构建时快照」。**这是 v0.5 的硬验收。**

**明确不做**：不写数据库、不做写接口（原计划留给 v0.6，**v0.6 已砍** → 持久化延后 v1.1）、不做认证、不做管理后台、不做 GraphQL。

**验收标准**
- [ ] `https://<你的服务>/docs` 公网可访问，OpenAPI 完整。
- [ ] `/api/v1/health` 返回 200 且包含依赖状态。
- [ ] 前端展示的数据确实来自 API（DevTools Network 可见）。
- [ ] **把服务停掉，刷新页面：站点仍然完整可读**，且给出友好提示。
- [ ] 仓库中无任何密钥；`git log -p | grep -i key` 无命中。
- [ ] CORS 拒绝非白名单来源（用 curl 带假 Origin 验证）。

**风险与对策**
- ⚠️ **免费实例休眠**：首次请求可能等 30–60 秒 → 前端**不等它**（首屏用构建期内容立即渲染），页脚显示「正在获取实时数据…」，3 秒拿不到就降级回内置内容；要避免冷启动则配定时探活（代价见 `api/README.md`：常驻约 720–744 实例小时/月，而免费额度是 750/月）。
- ⚠️ **免费额度变动**：部署前**必须现查一次**当前免费额度与休眠策略，不要相信记忆。**2026-10-11 复核**：HF Spaces 与 Fly.io 早已不可用；Render **实测要求加支付方式**（官方文档还写着不用，但创建服务时被拦），底线是不绑卡 → **改用 SnapDeploy**（D34，备选 Zeabur）。其免费档是 **100 容器小时/月且睡眠不计** —— 常驻一个月要 720 小时，**所以不能靠探活避免休眠**，睡着就是常态。详见 `docs/ARCHITECTURE.md` ADR-005 与 `api/README.md` 的部署一节。
- ⚠️ **作用域蔓延**：只做只读 API，忍不住加写接口会拖垮排期。**成功标准是「后端挂掉时站点照常完整可读」**，不是「后端永远不挂」。

**可砍**：`/notes/{slug}` 详情接口（前端本就有全文）。

### v0.7 —— AI 问答 RAG（11/09–12/06，4 周）★ 差异化

**目标**：做一个**只有你才有**的功能 —— 访客可以问「他做过哪些项目？会什么后端技术？」，AI 基于你的笔记/项目/简介作答，并**给出引用来源**。

**为什么这是最有价值的一版**：它同时展示嵌入（embedding）、向量检索、Prompt 工程、流式输出（SSE）、限流、缓存、成本控制、降级 —— 正好是你想学的 AI + 后端交叉领域，且面试时极易展开讲。
**为什么给 4 周**：它是唯一剩下的高风险项（SSE 未知、嵌入额度未知），**风险要早暴露**。

**第 1 步（新增，必须最先做）：SSE 探针**
依据：平台免费档把 WebSocket 划进付费的 Always-On，而 **SSE 会不会被平台缓冲 / 截断是未知的 —— 只有实测能回答**。
- 做法：在 `api/` 加一个 30 行以内的探针端点（每 500ms 推一行、共 20 行），**随下一次正常部署一起上**（不单独消耗部署配额），浏览器与 `curl` 各测一次，记录：首字节延迟 / 是否被缓冲 / 多少秒被截断。
- 结论二选一：**能流式 → 保持 SSE**；**不能 → 改非流式**（一次返回完整 JSON）。**这不是降级功能，只是换传输方式。**

**范围（做）**
1. **离线索引脚本** `api/scripts/build_index.py`：语料（notes + projects + profile）→ 分块（≈400 字，重叠 50）→ 嵌入 → 存 `api/data/index.json`。
   ⚠️ **索引随镜像发布**：免费档没有持久磁盘，写进磁盘的索引在每次唤醒后都没了 → 索引文件**提交进仓库**、构建进镜像（D28）。
2. ⚠️ **嵌入必须走 API**：512 MB / 0.25 vCPU 装不下 `sentence-transformers` + torch。选一个免信用卡的嵌入端点（**开工前现查**当前额度）。
3. **在线问答** `POST /api/v1/ask`：问题 → 嵌入 → 余弦相似度取 Top-4 → 组装 Prompt → LLM → 按第 1 步的结论用 SSE 或非流式返回。
4. **Prompt 约束**：只依据给定片段回答；无依据就回答「我的资料里没有这部分」；用 `[来源: 标题](链接)` 标注；不编造经历；不泄露系统提示词。
5. **成本与安全**：缓存（问题规范化后 hash → 24h 缓存，相同问题不打第二次）；限流（单 IP 10 次/日 + 全站每日总量上限）；熔断（达到上限或超预算 → 自动关闭并显示维护提示）；超时 20s → 降级到「请直接发邮件」。
6. **前端**：右下角浮层问答（来源链接 + 「AI 生成，可能有误」+「请勿输入敏感信息」常驻）。
7. 无 API Key 时功能自动隐藏，不影响站点。
8. **顺带加第 4 张项目卡**（轨道 B3 = 站点 v0.7，一次劳动两份收获）→ 项目卡 4 个。

**明确不做**：不引入向量数据库（语料只有几十条，JSON + 内存计算足够）；不做多轮对话记忆（留 `session_id` 字段占位即可）；不做微调/自训模型；不做语音、图片输入。

**验收标准**
- [ ] **SSE 探针有结论**：流式 or 非流式**已实测定型**，结论与实测数据（首字节延迟 / 是否缓冲 / 截断秒数）记录在案。
- [ ] 问「他做过哪些项目」能答对，且**引用来源链接可点开**。
- [ ] 问「今天天气怎么样」被拒绝或答「与我的资料无关」。
- [ ] 问一个资料里没有的问题，不编造，明确说没有。
- [ ] 相同问题第二次提问**不打 LLM**（日志可证，缓存命中）。
- [ ] 超过日限额后返回友好提示，站点其他功能不受影响。
- [ ] AI 浮层上「AI 生成，可能有误」与「请勿输入敏感信息」常驻可见。
- [ ] 运行日志中**不出现 API Key**。

**风险与对策**
- ⚠️ **SSE 被平台缓冲/截断** → 第 1 步的探针先回答；不能流式就换非流式，功能不减。
- ⚠️ 免费额度限速 → 选一个免费额度明确的 LLM 供应商，并**在实现前现查当前额度**；同时把供应商做成可替换（一个 `LLMProvider` 接口）。
- ⚠️ 幻觉 → Prompt 强约束 + 要求引用 + 「无依据则拒答」，并在 UI 上标注免责声明。
- ⚠️ 冷启动慢 → 索引随镜像发布、服务启动时加载（几十 KB，毫秒级）；嵌入调用加超时与重试。

**可砍（降级路径）**：把「问答」降级为**一次性的「AI 摘要」按钮**（对选定内容生成摘要），或降级为「基于关键词的站内搜索」。**AI 功能只要有，就比没有强。**

1. `git tag -a v1.0.0 -m "release v1.0.0"` 并推送。
2. 写 `CHANGELOG.md` 的 v1.0.0 段落（新增 / 变更 / 修复 / 已知问题）。
3. 更新仓库 About、Topics、主页链接、README 顶部徽章。
4. 在 GitHub 发 Release（附简短说明与链接）。
5. 对外公告（朋友圈 / 技术社区 / 班级群），文案含：一句话定位 + 站点链接 + GitHub 链接。
6. 发一篇「我从 v0.1 做到 v1.0 学到了什么」的复盘笔记（**这篇本身就是最好的作品**）。
7. 归档：把 v1.0 的架构图与检查清单存进 `docs/`。

**发布后（1 月，考试周，低强度）**：只做修复，不加功能；收集 3–5 个人的反馈写进 `docs/FEEDBACK.md`，作为 v1.1 的输入。

## 6. 需求保险丝（落后时按此顺序砍）

**第一原则：砍范围，不砍质量；砍功能，不砍作品。**

**最小可发布集（Must，任何情况下都必须完成）**
- ✅ v0.2 工程基线 + 内容数据化
- ✅ v0.3 笔记系统（精简版：列表 + 详情，无 RSS / 无搜索）
- ✅ v0.4 门面达标（移动端可用 + 基本无障碍）
- ✅ v0.5 后端只读 API 上线 + 前端降级
- ✅ v0.7 AI 功能（**允许降级**为 AI 摘要或关键词搜索）
- ✅ 3 个真实项目（轨道 B1/B2/B3）
- ✅ 文档 + CHANGELOG + tag + 发布检查清单

**砍单顺序（从先砍到后砍）**
1. v0.6 数据库与留言板 —— **已砍**（2026-10-11，平台免费档无持久磁盘、无免费数据库）
2. v0.4 的简历 PDF、OG 图片、明暗主题
3. v0.3 的 RSS、站内搜索、代码高亮
4. v0.7 降级：RAG 问答 → AI 摘要 → 关键词搜索
5. v0.8 的 CSP 头、性能预算说明（保留依赖扫描与密钥检查）
6. v0.4 的标签筛选、项目封面图
7. v0.2 的 ESLint、Lighthouse CI（**体积门禁与两条黑盒冒烟不列入可砍** —— 它们是 Must 底线的自动化）

**绝对不砍（底线）**
- ❌ 内容与代码分离（否则每次更新都会烂尾）
- ❌ API 不可用时的前端降级
- ❌ 密钥不入库
- ❌ 3 个真实项目 + 简历/联系方式可达
- ❌ CHANGELOG + 版本 tag
- ❌ 移动端真机检查

**触发降级的判断点（每个版本结束时自检）**
> 原日期（11/29、12/20 等）随 2026-10-11 的重排**全部失效**，以这五条为准。

- 若某版本超出计划 **> 5 天**：立即执行砍单顺序，禁止顺延后续版本。
- **11/16 前**：SSE 探针必须有结论。平台不支持流式 → 立即改非流式（只换传输方式，不降功能）。
- **11/30 前**：v0.7 的「索引 + 检索」必须跑通（还没接 LLM 也算）。否则启动降级：RAG → AI 摘要 → 关键词搜索。
- **12/10 前**：v0.8 的依赖扫描与 README 30 分钟验证必须完成。
- **12/20 前**：v0.9 的清单、回滚演练、3 人反馈必须完成。
- **12/24**：若仍有 Must 项未完成 → **缩小 Must 集**（先砍封面图 / 美化 / `notes-collection`），保 12/27 发布。

## 7. 每周节奏（照着做就行）

| 时间 | 做的事 | 时长 |
| :--- | :--- | :--- |
| 周一晚 | 打开 Claude Code，粘贴本周版本的指令；确认本次只推进 1–2 条验收标准 | 0.5 h |
| 周二–周四晚 | 每次只攻一条验收标准；跑一次 `npm run check` | 1.5 h × 3 |
| 周五晚 | 跑完整质量门禁 → 合并 → 部署 → 打 tag（如到版本末） | 1.5 h |
| 周六 | 写本周笔记（≥ 1 篇）；更新「近况」 | 1.5 h |
| 周日 | 缓冲：补课、复盘、看别人的作品；写 3 行周复盘 | 1 h |
| 每版本末 | 让 Claude Code 生成本版复盘（做了什么/学到什么/欠了什么） | 0.5 h |

**三条纪律**
1. **一次只推一条验收标准。** 同时开三件事 = 三件都做不完。
2. **每周必须有一次对外可见的变化**（哪怕只是一篇笔记）。避免「憋大招」。
3. **不确定就降级，不要卡住。** 卡超过 2 小时，就在 Claude Code 里问：「有没有更简单的实现方式？」并记录取舍。
