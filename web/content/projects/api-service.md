## 背景

「前端点一下按钮，数据到底是怎么被取出来的」——这个问题光看教程看不明白，得自己写一个服务放在中间才算数。

正好这个作品集也需要这一层：与其把内容写死在页面里，不如让后端把它作为接口吐出来，前端只负责显示。

## 实际做了什么

7 个 GET 端点：6 个内容接口（profile / projects / notes / now 等）+ 1 个健康检查，全部只读。FastAPI 顺手给的 /docs 交互式文档也在，浏览器里可以直接点着测。

- **分层**：routers 只碰 HTTP（路径、查询参数、状态码），services 负责读内容、拼数据，models 用 Pydantic 声明响应的形状。
- **统一错误体 + X-Request-Id**：出错时返回同一个形状（错误码 + 人话说明），每个响应都带一个 X-Request-Id，排查时能顺着这个 ID 去日志里捞出具体那一次请求。
- **契约测试**：Python 侧的解析规则是照前端的 `content-schema.js` 重写的，两份实现到底一不一致，靠一份由 Node 跑出来的 fixture 逐字段比对 —— 不靠人读代码点头。
- **部署**：打进 Docker 镜像，部署在免费 PaaS 上。
- **前端降级**：接口取不到数据时不白屏，3 秒超时后回退到构建期内置的那份内容。

## 难点与收获

1. **一份内容，两边读。** 后端不另建数据源，直读 `web/content/` 下的 `.md` —— 和前端构建时读的是同一批文件。好处是改一篇文章不用同步两处；代价是「内容格式」成了前后端共同的契约，动它得两边一起动。

2. **免费档会休眠，而且叫不醒。** 实测连打 19 次接口、整整 97 秒，回回都是 503 的唤醒页 —— 光发请求轮询 90 秒也没能把它叫起来；只有**用浏览器打开那个 URL**（把唤醒页真正渲染出来）才会触发启动，大约 60 秒后恢复。所以前端的超时定成 3 秒：与其让页面干等，不如直接回退到构建期内置的那份内容。有意思的是，项目卡上那个链接本身就是「用浏览器打开」—— 点一下正好把它唤醒。

3. **镜像里内容被静默排除了。** `.dockerignore` 里写了 `**.md` 一刀切，看着只是「少拷点文档」，其实把 `projects/` 与 `notes/` 的 `.md` 一起排掉了；而 `profile.json` 是 `.json`，照旧进镜像 —— 于是 `/health` 依然报 ok，只有项目区和笔记区变成空的。构建不失败、不报错，比 503 难发现得多。最后靠镜像里的冒烟测试（断言 projects / notes 数量大于 0）才照出来。

**没做什么**：没有写接口 —— POST / PUT / DELETE 一个都没有，这个服务就是只读的；也没有数据库，内容直接来自仓库里的文件。真正的读写和 SQLite 留给 v0.6，这次先拿只读把 HTTP 这条链路走通。
